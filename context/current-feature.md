## Notes

<!-- Additional context, constraints, or details from spec -->
- This is a much bigger architectural change than the last two features — it replaces the app's entire data layer, which currently lives outside this repo entirely (a separate ASP.NET Core Web API, per `DELI_API_ROOT` in `src/Constants.js`). Endpoints currently consumed: `GET /api/MenuItems`, `GET /api/MenuItems/grouped`, `GET /api/MenuItems/sandwiches`, `PUT /api/MenuItems/{id}` (multipart, incl. image upload).
- Ironic timing: the `remove-unused-code` feature deleted the old `backend/` (Express) and `functions/` (Firebase Functions) directories as dead weight since nothing in `src/` called them. This feature effectively needs to stand up a *new* backend service — need to decide whether that's Firebase Functions again, a standalone Node/Express service, or something else, and where it deploys/runs.
- Open questions to resolve with user before writing code: where does the new API layer live and get hosted; how does the Postgres schema map to the existing item shape (`category`, `basePrice` vs. `prices: [{ size, price }]`, `imageUrl`); how does image upload/storage work now (old backend used Firebase Storage); how existing menu data gets migrated/seeded into Neon; whether this is a big-bang cutover or the .NET API stays as a fallback during rollout; how `DATABASE_URL`/Neon credentials are stored (env var, gitignored — must not repeat the committed-secret incident from `remove-unused-code`).
- Given the user is new to Neon/Prisma and asked to be walked through it, favor an incremental, explained approach (e.g. schema first, then one endpoint at a time) over a single large opaque change, and keep comments where the non-obvious "why" of Prisma/Neon-specific setup would otherwise be a mystery.
- Decisions made with user: new API is a standalone Node/Express service (in `server/`, this repo), not Firebase Functions. Cutover is incremental, one endpoint at a time — new API runs alongside the .NET one; `src/Constants.js`'s `DELI_API_ROOT` doesn't get flipped until each endpoint is verified.
- Schema: `MenuItem` (name, description, imageUrl, category, basePrice) + related `Price` rows (size/price pairs, for sandwiches' size-based pricing) — mirrors the .NET API's `{ ..., basePrice, prices: [{size, price}] }` shape so responses can stay a drop-in match.
- Neon gives both a pooled (`-pooler` host, for app runtime) and direct (for migrations) connection string — schema.prisma uses `DATABASE_URL` (pooled) + `directUrl = DIRECT_URL` (direct), both env vars in `server/.env` (gitignored, never pasted into chat).
- Seed data (`server/prisma/seed-data.json`) was pulled directly from the user's running local .NET API (`GET /api/MenuItems/grouped`, 54 items) rather than hand-written, so the new DB starts with real menu content.
- Decision made: image uploads go to Cloudinary (not local disk, not Firebase Storage again) — avoids both the ephemeral-filesystem problem of most free PaaS hosts and reusing the credential setup that caused the earlier secret-leak incident.
- Known follow-up before cutover: `SandwichItem.jsx` always does `src={`/images/sandwiches/${item.image}`}`, assuming a bare local filename. Once a sandwich's photo is edited through the new `PUT` endpoint, `imageUrl` becomes a full `https://res.cloudinary.com/...` URL and that prefixing breaks the image. Needs a small frontend fix (skip the prefix when the value already looks like a URL) before flipping `DELI_API_ROOT` over.
- Near-miss: while setting up Cloudinary, real API credentials were briefly pasted into `server/.env.example` (not gitignored) instead of `server/.env` (gitignored) — caught before anything was committed, user moved them to the correct file. `.env.example` confirmed to still contain only placeholders.
- `node --watch` (used by `npm run dev`) only restarts on `.js` file changes, not `.env` edits — the server has to be restarted manually after editing `server/.env`, which caused a confusing "Must supply api_key" error the first time despite `.env` being correct, until restarted.
- Bug fixed: `multer`'s upload-size-limit errors bypassed the route handler's try/catch (multer's middleware runs before the handler and calls Express's error path directly on failure) and returned Express's default HTML error page instead of JSON, which would have broken the frontend's `res.json()` parsing. Added a 4-arg Express error-handling middleware in `server/src/index.js` to return `{ error: ... }` JSON with a 400 status for `MulterError`s instead.
