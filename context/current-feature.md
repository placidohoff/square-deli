## Goals

<!-- Bullet points of what success looks like -->
- Real login gating the admin section — spec explicitly frames this as needed ("Would need a login to get to the admin section"), implying the current hardcoded `admin1`/`admin789` client-side check in `src/pages/Edit.jsx` isn't sufficient/isn't "real" login.
- Phase 1: menu item price and description updates work through the admin UI.
- Phase 2 (explicitly sequenced after phase 1 per spec): image updates work through the admin UI.

## Notes

<!-- Additional context, constraints, or details from spec -->
- Spec explicitly phases the work: "First work on updating prices and descriptions, then images." Don't try to do everything at once.
- This picks up directly where `neon-postgres-migration` left off — that feature built and curl-verified the backend (`PUT /api/MenuItems/{id}` on the new `server/` Express+Prisma API, incl. Cloudinary image upload) but explicitly deferred verifying it through the real `/edit` UI to "a separate future feature." This is that feature.
- Current state of the admin UI: `Edit.jsx` gates access with a hardcoded `admin1`/`admin789` check done entirely in the frontend (no real backend auth call) — the spec's "would need a login" suggests replacing this with something real.
- `EditItemCard.jsx` (sandwiches) already has name/description/basePrice/size-prices/image inputs and calls the real `PUT` endpoint. `EditItemCardCharlie.jsx` (other meals categories) currently only has name + basePrice inputs — no description or image fields at all — so "phase 1: prices and descriptions" isn't even fully wired up for non-sandwich items yet; that's real, not just untested.
- Open questions to resolve with user before writing code: does real login mean backend-issued auth (e.g. a `/login` endpoint on `server/`, session cookie or JWT, admin credentials stored server-side) or just a better frontend gate; if backend auth, does the admin credential live in `server/.env` (a single hardcoded admin user is plausible for a one-person deli, no need for a users table necessarily); how the frontend persists being logged in (cookie vs localStorage token) and for how long.
